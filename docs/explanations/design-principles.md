# Design principles

1. **Runtime-agnostic.** The language specification is independent of any runtime, host, or execution target. Programs can run in browsers, game engines, servers, CLI tools, type-level contexts, embedded hardware, or GPUs — the host determines the execution model. The language does not constrain _where_ or _how_ programs execute.
2. **Declarative.** A document describes _what_ values it contains, not _how_ to compute them. Computation is expressed through field declarations and host-provided functions, not imperative code.
3. **Schema-optional.** Schemas define types when present. The `$:` section is a convention of the canonical dialect, not a language-level requirement. A host may use any schema system, or none — the kernel evaluates expressions regardless.
4. **Named functions are emergent.** The language defines no built-in functions and no `functions:` keyword. A function is just an object with a `body` field stored in a field. The `apply` host primitive evaluates function bodies with bound arguments. User-defined functions compose from host primitives and each other — no new language constructs needed.
5. **Composition over keywords.** The language has a small set of primitives. Complex patterns (imports, config spreading, conditional loading) emerge from composition, not from dedicated syntax.
6. **Format-agnostic.** Documents can be written in YAML, JSON, TOML, or any format that maps to JSON-compatible values.
7. **Embeddable.** The core is a small kernel designed to be embedded in a host application, not a standalone language ecosystem. The AST has zero dependencies. The host provides all functions; the kernel evaluates expressions and returns values. This is the Lua/Rhai embedding model, not the Python/Unison model. No runtime owns the codebase, no toolchain must be shipped, no garbage collector is imposed on the host.
8. **Host provides the world.** The language defines no built-in functions, no standard library, no I/O primitives. Everything the evaluator can do is provided by the host via the `Host` trait. The host decides which functions exist, which namespaces are available, and what side effects are permitted. The language is a pure evaluation kernel; all policy lives in the host.
9. **Content addressing is optional.** Definitions can be identified by hash (SHA-256 of canonical JSON) for deduplication, reproducible builds, and cross-machine sharing. But content addressing is a storage layer, not a language-level constraint. Documents evaluate correctly without ever touching a `DefinitionStore`. The language does not require a codebase database, hash-based imports, or a package manager to function.
10. **Control flow is emergent, not built-in.** The language defines no conditional, loop, pattern-matching, or let-binding syntax. These emerge from host functions operating on first-class function values: `if(cond, then_fn, else_fn)` evaluates the matching branch via `apply`, `map(items, fn)` iterates in the host, `match(value, cases)` dispatches by structure. Let-bindings are just function parameters — `apply(fn(x) { ... }, value)` binds `x` to `value`. The language provides the evaluation kernel (literals, path lookups, function calls, handlers); the host provides the control flow. This keeps the syntax small while allowing a host that provides `if`, `map`, `match`, `filter`, `reduce` to reach arbitrary computational expressiveness — the scope boundary is in what the _language_ bakes in, not in what a _host_ can provide.
11. **Tree-shakeable.** Major subsystems are gated by Cargo features. A host enables only the capabilities it needs, and the compiler omits the rest.
12. **Progressive Enhancement.** Abstract is common minor denominator, but we can progressively enhance like once Browser APIs are available, etc.
13. **Everything is a plugin.** Every concept in the language is a `Plugin`: syntax, semantics, tooling, targets, the garbage collector, the sandbox, the standard library. A `Host` is an empty composer that loads kits and plugins and dispatches `CapabilityRequest`s. Nothing is hard-coded in the kernel except the composition primitives (`Plugin`, `Host`, `Operation`, `Behavior`, `RuleAcceptor`, `Contribution`). There is no privileged subsystem.
14. **Evaluation is an operation, not a subsystem.** There is no separate "VM" layer. Evaluation is the `Eval` operation, defined by `handl-ext-eval` and served by `EvalBehavior` rules contributed by target plugins. The interpreter is a target plugin (`handl-target-rust-interpreter`), not a peer abstraction alongside the platform. A wasm or JIT target registers its own `EvalBehavior` rules; no `VirtualMachine` trait sits between them.
15. **Garbage collection is a plugin.** A GC strategy is provided by a target or library plugin and selected by the host. The kernel imposes no GC. A host may run with no GC, a reference-counting GC, a tracing GC, or a region-based collector — all are plugin choices, not language-level constraints.
16. **Sandboxing is a kit/plugin property.** Whether a program runs sandboxed is determined by which stdlib plugins are exposed and which target plugin runs it, not by a kernel flag. A kit that exposes only pure modules and selects a non-IO target produces a sandbox; a kit that exposes `fs`, `env`, and `http` over a native target does not. The kernel has no sandbox concept.
17. **Targets are plugins.** A target plugin provides the execution backend (interpreter, compiler, JIT, wasm runtime) by contributing `EvalBehavior` rules. Targets are not a separate layer above plugins — they are plugins. The `handl-target-*` crates are plugins like any other.
