# Hot Module Replacement (HMR)

## Context

handl documents are loaded by the module resolver and evaluated by the VM.
During development, changing a document while the program is running currently
requires stopping the process and starting again. This is acceptable for
short-lived programs but painful for long-running ones — servers, watchers,
streaming pipelines — where you want to iterate without losing in-flight
state, event logs, or pending operations.

Vite's HMR design provides a proven mental model: a WebSocket channel between
dev server and runtime, and explicit lifecycle hooks (`accept`, `dispose`,
`decline`, `invalidate`, `prune`) that let a module control what happens when
it changes. We adapt that model to handl documents.

HMR is a language toolchain concern: it watches handl documents, computes
a diff, and sends it to the runtime. Hosts (including Peregrin) can layer
their own HMR semantics on top — e.g. preserving workflow execution state
across module swaps — but the core diff/patch protocol is language-level.

## Decision

handl provides an HMR module (`handl-hmr`) and an `handl dev` command. The module
provides a dev server that watches document files, computes a minimal update
delta, and sends it to the runtime over a WebSocket. The runtime applies the
delta through the module resolver while honouring lifecycle hooks declared
in the document.

### Components

```text
┌──────────────┐     file change     ┌──────────────┐
│  handl     │  ────────────────▶  │  HmrServer   │
│  documents   │                     │  (dev tool)  │
└──────────────┘                     └──────┬───────┘
                                            │ WebSocket
                                            ▼
                                     ┌──────────────┐
                                     │  HmrClient   │
                                     │  (runtime)   │
                                     └──────┬───────┘
                                            │
                                            ▼
                                     ┌──────────────┐
                                     │  Module      │
                                     │  Resolver    │
                                     │  (swap /     │
                                     │   reload)    │
                                     └──────────────┘
```

- **`HmrServer`** (dev server). Watches document files and any `import()`
  paths. On change, reloads the document, computes a minimal diff (`added`,
  `removed`, `changed` declarations), and sends it to the runtime. Falls back
  to `full-reload` when a change cannot be applied safely.
- **`HmrClient`** (runtime). Receives WebSocket messages inside the running
  process, validates them, and forwards them to the update handler.
- **`HmrUpdateHandler`**. Applies the diff to the running module. It retires
  removed declarations, injects new ones, and replaces changed declarations
  for which the author has opted in. It emits lifecycle events before and
  after each operation.
- **`HmrUpdate` schema**. A typed JSON message describing the delta. It is
  the boundary contract between dev server and runtime.

### WebSocket protocol

Messages are JSON over WebSocket.

Client to server (optional):

- `{ "type": "hmr:ready" }`
- `{ "type": "hmr:custom", "payload": ... }`

Server to client:

- `{ "type": "hmr:update", "added": [...], "removed": [...], "changed": [...] }`
- `{ "type": "hmr:full-reload", "reason": "..." }`
- `{ "type": "hmr:error", "error": "..." }`

### Document surface

`hmr` may appear at the document level and on individual declarations.
Declaration-level settings override document-level defaults.

Document-level:

```yaml
hmr:
  accept: [field_a, field_b]
  before: log("pausing for HMR")
  after: log("resumed from HMR")
  on_error: full-reload
```

Declaration-level:

```yaml
fields:
  counter:
    type: number
    expr: |
      prev + 1
    hmr:
      accept: true
      dispose: log("cleaning up counter")
      data:
        counter: prev
```

Fields:

- `accept` (boolean or list of names). Whether the changed declaration can
  be replaced in place. If `false`, the dev server falls back to
  `full-reload`.
- `decline` (list of names). Declarations that always force `full-reload`
  when changed.
- `before` / `after`. Expressions to evaluate before and after the HMR delta
  is applied. Lets the program pause I/O, flush buffers, or re-arm listeners.
- `dispose`. Expression to evaluate before an old declaration is removed or
  replaced. Used to persist or clean up state.
- `prune`. Expression to evaluate after a declaration is removed.
- `data`. A map of values to carry across updates for the same declaration.
  Values can be read from the previous evaluation and written back on
  `dispose`.
- `invalidate`. A list of downstream declarations that must also be reloaded
  when this one changes.
- `on_error` (document-level only). One of `full-reload`, `cancel`, or
  `ignore`.

### Lifecycle

1. The dev server detects a file change.
2. It reloads the document, validates it, and computes a diff.
3. If any changed or removed declaration is not accepted for HMR, the server
   sends `hmr:full-reload` and the runtime restarts.
4. For an accepted delta:
   - Evaluate `before` expressions.
   - For removed declarations, evaluate `dispose` and `prune`, then remove.
   - For changed declarations, evaluate `dispose`, remove the old definition,
     inject the new definition, and restore any `data` values.
   - For new declarations, inject them.
   - Evaluate `after` expressions.

### Host integration

Hosts can extend HMR by registering custom update handlers. For example,
Peregrin's host might preserve workflow execution state (event log, pending
events, node fire counts) across module swaps, adding orchestration-specific
semantics to the base HMR protocol.

## Consequences

- Long-running handl programs can be edited and iterated on without a full
  process restart.
- The module resolver gains `swap` and `reload` primitives as first-class
  operations.
- Authors get explicit control over state preservation and teardown through
  lifecycle hooks.
- The dev server adds a WebSocket dependency. It must only be used in local
  development; remote HMR is out of scope for the first version.
- Invalidation and full-reload must be carefully defined so that a partially
  applied update does not leave the program in an inconsistent state.
